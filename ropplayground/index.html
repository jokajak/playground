ROP Playground

Learn how return-oriented programming chains work — then prove it by building chains yourself.

What this is A conceptual sandbox. The "CPU" here is a toy simulator written in JavaScript — there is no real binary, no real memory, and nothing you build here does anything to your computer. It exists so the mechanics of a ROP chain become something you can poke at, the way exercises like ROP Emporium teach them.

Why return-oriented programming exists

The classic stack-overflow attack was simple: overflow a buffer, overwrite the saved return address so it points into your own buffer, and fill that buffer with raw CPU instructions ("shellcode"). When the function returned, the CPU jumped into your bytes and ran them.

Defenders killed that with NX / DEP (the "No-eXecute" bit, Data Execution Prevention): memory pages are now either writable or executable, never both. Your buffer is writable, so the CPU refuses to execute it. Injected shellcode is dead on arrival.

ROP is the answer to that. The insight: you don't need to inject new code if the program already contains all the code you need — in libraries like libc, in the program itself. You can't write new instructions, but you can still control the stack, and the stack is what decides where each ret goes next. So instead of writing code, you write a list of addresses of code that is already there, and let the CPU's own ret instruction walk down your list.

The one instruction that makes it work: ret

On x86-64, ret does exactly two tiny things:

# ret is literally equivalent to:
pop rip      # take the 8 bytes at the top of the stack, make them the next instruction address
             # (pop also advances rsp by 8, so the stack "moves down" to the next slot)

That is the whole trick. If you control the stack, every ret is a jump to an address you chose. Put a second useful snippet's address in the next slot, and when it ends in ret, the CPU pops that and jumps again. One ret hands off to the next, down the stack, forever.

Gadgets

A gadget is a short run of instructions that happens to end in ret. You find them scattered throughout existing code. Each gadget does one small useful thing and then hands control back to the stack. A few classics:

pop rdi ; retTake the next value off the stack into register rdi, then return. This is how you load an argument you control.
pop rsi ; retSame, for rsi (the 2nd argument register).
mov [rdi], rsi ; retA "write-what-where": store the value in rsi into the memory address in rdi. Used to plant a string like /bin/sh into memory.
syscall ; retMake a kernel call using whatever is currently in the registers.
Calling convention (System V, x86-64) When you call a function, arguments go in registers in this order: rdi, rsi, rdx, rcx, r8, r9. For a raw syscall, the syscall number goes in rax and arguments in rdi, rsi, rdx, .... So "set up the registers, then call" is the recurring shape of every chain.

What a chain looks like on the stack

Say you want to call a function win(0xdeadbeef) that already exists in the program. You need rdi = 0xdeadbeef and then to jump to win. You find a pop rdi ; ret gadget. Here is the stack you build (top = lowest address = what executes first): 

stack (grows downward in address; ret reads top-first)
┌────────────────────────┬──────────────────────────────────────┐
│ &(pop rdi ; ret)        │ 1. ret jumps here. It runs "pop rdi".  │
├────────────────────────┼──────────────────────────────────────┤
│ 0x00000000deadbeef      │ 2. "pop rdi" eats THIS slot → rdi       │
├────────────────────────┼──────────────────────────────────────┤
│ &win                    │ 3. the gadget's own "ret" jumps here    │
└────────────────────────┴──────────────────────────────────────┘

Step by step, the CPU does:

  1. The overflow put &(pop rdi ; ret) where the return address was. The vulnerable function's ret jumps there.
  2. pop rdi runs: it pops the next slot (0xdeadbeef) into rdi and advances the stack.
  3. The gadget's ret runs: it pops the next slot (&win) into rip. Now we're executing win — with rdi already set to the argument we wanted.

That's a complete, if tiny, ROP chain. Longer chains just repeat the idea: each gadget sets up a little state, and its trailing ret pulls the next address off the stack. The Simulator tab lets you build exactly this and watch it run. The Challenges tab gives you goals and makes you figure out the chain.

Reality check Real-world ROP adds layers this toy skips: finding gadgets in an actual binary (ROPgadget, ropper), defeating ASLR (addresses are randomized, so you usually need an info-leak first), stack canaries, and byte-level constraints (no null bytes, alignment). The logic of chaining, though, is exactly what you'll practice here.
